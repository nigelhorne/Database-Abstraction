  129: =head1 DESCRIPTION
  130: 
  131: C<Database::Abstraction> is a read-only ORM for Perl that gives a uniform
  132: interface over CSV, PSV, TSV, JSON, XML, SQLite, DBM::Deep, BerkeleyDB, and
  133: Excel (XLS/XLSX) files - local, remote (via SSH), or fetched from a URL -
  134: without writing any SQL.
  135: Effectively it allows you to access a database table, of many different
  136: database formats, as an object.
  137: 
  138: Key features:
  139: 
  140: =over 4
  141: 
  142: =item *
  143: 
  144: B<No SQL required.>  Use plain Perl method calls for simple lookups and
  145: scans; switch storage formats without changing application code.
  146: 
  147: =item *
  148: 
  149: B<Rich query criteria.>  Pass plain values, SQL wildcards, C<undef> (IS NULL),
  150: comparison operators (C<< > >> C<< < >> C<< >= >> C<< <= >> C<!=>), pattern
  151: operators (C<-like>, C<-not_like>), set operators (C<-in>, C<-not_in>,
  152: C<-between>), and logical groupings (C<-or>, C<-and>).
  153: 
  154: =item *
  155: 
  156: B<Automatic joins.>  Add a C<join> parameter to any select method to
  157: combine tables with INNER, LEFT, RIGHT, FULL, or CROSS joins.
  158: 
  159: =item *
  160: 
  161: B<Chained query builder.>  The C<query()> method returns a
  162: L<Database::Abstraction::Query> object for fluent, composable queries:
  163: C<< $db->query->where(...)->order_by(...)->limit(...)->all() >>.
  164: 
  165: =item *
  166: 
  167: B<Schema introspection.>  C<columns()> lists column names; C<schema()>
  168: returns full type/nullability metadata, using native driver introspection
  169: (C<PRAGMA table_info> for SQLite, C<column_info> for others).
  170: 
  171: =item *
  172: 
  173: B<DSN portability.>  Pass a C<dsn> (plus optional C<username>/C<password>)
  174: to connect to any DBI-supported database (SQLite, PostgreSQL, MySQL, ...)
  175: instead of pointing at a local file.
  176: 
  177: =item *
  178: 
  179: B<Performance.>  Small files are slurped into a RAM hash for sub-millisecond
  180: lookups.  All DBI statement handles are cached with C<prepare_cached()>.
  181: A CHI-compatible cache layer is also supported.
  182: 
  183: =back
  184:

  289: =head1 FILE FORMATS
  290: 
  291: The module probes the C<directory> for files in this priority order:
  292: 
  293: =over 4
  294: 
  295: =item 1. C<SQLite>
  296: 
  297: File ending C<.sql>, C<.sqlite>, or C<.sqlite3>.
  298: Requires L<DBD::SQLite>.
  299: 
  300: =item 2. C<Deep>
  301: 
  302: DBM::Deep file ending C<.dbm> or C<.deep>.  The entire file is slurped
  303: into a plain Perl hash on open; all in-memory fast-paths apply.
  304: Requires L<DBM::Deep> (loaded lazily).
  305: 
  306: =item 3. C<PSV>
  307: 
  308: Pipe-separated file, ending C<.psv>.
  309: 
  310: =item 4. C<TSV>
  311: 
  312: Tab-separated file, ending C<.tsv>.
  313: 
  314: =item 5. C<CSV>
  315: 
  316: Comma (or custom) separated file, ending C<.csv> or C<.db>; can be
  317: gzipped (C<.csv.gz> or C<.db.gz>).
  318: B<Note:> the default separator is C<!> not C<,> for historical
  319: reasons - pass C<< sep_char => ',' >> for standard CSVs.
  320: Requires L<Text::xSV::Slurp> for the slurp fast-path (loaded lazily).
  321: 
  322: =item 6. C<Excel> (C<.xls>) and C<XLSX> (C<.xlsx>)
  323: 
  324: Two separate Excel backends - one per file format:
  325: 
  326: =over 4
  327: 
  328: =item B<.xls> - old binary format, opened via L<DBD::Excel> (which uses
  329: L<Spreadsheet::ParseExcel> internally).  All queries go through DBI/SQL;
  330: no in-memory slurp path.  C<max_slurp_size> has no effect.
  331: 
  332: =item B<.xlsx> - modern OOXML format, parsed directly via
  333: L<Spreadsheet::ParseXLSX> and slurped into an in-memory hash (keyed mode)
  334: or array (C<no_entry> mode).  No DBI handle is created; all queries use
  335: the in-memory fast-path.  Complex criteria (operator hashes, C<-or>/C<-and>)
  336: will fall through to the SQL path and croak - use simple scalar criteria.
  337: 
  338: =back
  339: 
  340: For both formats, each worksheet is a separate logical table; the active
  341: worksheet is determined by the class-derived table name (or the C<table>
  342: constructor parameter).  Both modules are loaded lazily.
  343: 
  344: =item 7. C<XML>
  345: 
  346: File ending C<.xml>.
  347: Requires L<XML::Simple> for the slurp fast-path (loaded lazily).
  348: 
  349: =item 8. C<JSON>
  350: 
  351: File ending C<.json>, slurped into memory via L<JSON::MaybeXS> (loaded
  352: lazily).
  353: 
  354: The file may contain either a JSON array of row objects:
  355: 
  356:     [
  357:       { "entry": "key1", "col": "val1" },
  358:       { "entry": "key2", "col": "val2" }
  359:     ]
  360: 
  361: or a JSON object whose keys are the primary-key values:
  362: 
  363:     {
  364:       "key1": { "col": "val1" },
  365:       "key2": { "col": "val2" }
  366:     }
  367: 
  368: In the object form, each key is injected into its row hash under the C<id>
  369: column name (default C<entry>), so all normal lookups work identically to
  370: the array form.
  371: 
  372: A zero-byte or whitespace-only file is treated as empty - all query methods
  373: return 0 / C<undef> / C<[]> without throwing.
  374: Requires L<JSON::MaybeXS> (loaded lazily).
  375: 
  376: =item 9. C<BerkeleyDB>
  377: 
  378: Binary key-value file ending C<.db>.
  379: 
  380: =item 10. C<HTML>
  381: 
  382: HTML page fetched via a C<url>.  Pass C<url => 'https://...'> instead of
  383: C<directory>; the module fetches the page with L<LWP::UserAgent::Cached>, parses all
  384: C<< <table> >> elements with L<HTML::TableExtract>, and slurps the first (or
  385: C<html_table_index>-selected) table into memory.  The first row of the table
  386: is treated as column headers.  Both modules are loaded lazily and are not
  387: required for other backends.
  388: 
  389: =back
  390: 
  391: Pass C<dsn> to bypass file detection entirely and connect via any DBI driver.
  392: Pass C<url> to fetch and slurp data from a remote source without a local
  393: directory.  When the URL returns C<Content-Type: application/json> or the URL
  394: path ends in C<.json>, the response is parsed as JSON (see item 8 above).
  395: Otherwise the response is parsed as an HTML page (item 10).

  428:     score => { '!=' => 0   }   # score != 0

  432:     score => { '>' => 60, '<' => 90 }   # 60 < score < 90

 1457:

 1468:
