  189: =head1 DESCRIPTION
  190: 
  191: C<Database::Abstraction> is a read-only ORM for Perl that gives a uniform
  192: interface over CSV, PSV, TSV, JSON, XML, SQLite, DBM::Deep, BerkeleyDB, and
  193: Excel (XLS/XLSX) files - local, remote (via SSH), or fetched from a URL -
  194: without writing any SQL.
  195: Effectively it allows you to access a database table, of many different
  196: database formats, as an object.
  197: 
  198: Key features:
  199: 
  200: =over 4
  201: 
  202: =item *
  203: 
  204: B<No SQL required.>  Use plain Perl method calls for simple lookups and
  205: scans; switch storage formats without changing application code.
  206: 
  207: =item *
  208: 
  209: B<Rich query criteria.>  Pass plain values, SQL wildcards, C<undef> (IS NULL),
  210: comparison operators (C<< > >> C<< < >> C<< >= >> C<< <= >> C<!=>), pattern
  211: operators (C<-like>, C<-not_like>), set operators (C<-in>, C<-not_in>,
  212: C<-between>), and logical groupings (C<-or>, C<-and>).
  213: 
  214: =item *
  215: 
  216: B<Automatic joins.>  Add a C<join> parameter to any select method to
  217: combine tables with INNER, LEFT, RIGHT, FULL, or CROSS joins.
  218: 
  219: =item *
  220: 
  221: B<Chained query builder.>  The C<query()> method returns a
  222: L<Database::Abstraction::Query> object for fluent, composable queries:
  223: C<< $db->query->where(...)->order_by(...)->limit(...)->all() >>.
  224: 
  225: =item *
  226: 
  227: B<Schema introspection.>  C<columns()> lists column names; C<schema()>
  228: returns full type/nullability metadata, using native driver introspection
  229: (C<PRAGMA table_info> for SQLite, C<column_info> for others).
  230: 
  231: =item *
  232: 
  233: B<DSN portability.>  Pass a C<dsn> (plus optional C<username>/C<password>)
  234: to connect to any DBI-supported database (SQLite, PostgreSQL, MySQL, ...)
  235: instead of pointing at a local file.
  236: 
  237: =item *
  238: 
  239: B<Performance.>  Small files are slurped into a RAM hash for sub-millisecond
  240: lookups.  All DBI statement handles are cached with C<prepare_cached()>.
  241: A CHI-compatible cache layer is also supported.
  242: 
  243: =back
  244:

  349: =head1 FILE FORMATS
  350: 
  351: The module probes the C<directory> for files in this priority order:
  352: 
  353: =over 4
  354: 
  355: =item 1. C<SQLite>
  356: 
  357: File ending C<.sql>, C<.sqlite>, or C<.sqlite3>.
  358: Requires L<DBD::SQLite>.
  359: 
  360: =item 2. C<Deep>
  361: 
  362: DBM::Deep file ending C<.dbm> or C<.deep>.  The entire file is slurped
  363: into a plain Perl hash on open; all in-memory fast-paths apply.
  364: Requires L<DBM::Deep> (loaded lazily).
  365: 
  366: =item 3. C<PSV>
  367: 
  368: Pipe-separated file, ending C<.psv>.
  369: 
  370: =item 4. C<TSV>
  371: 
  372: Tab-separated file, ending C<.tsv>.
  373: 
  374: =item 5. C<CSV>
  375: 
  376: Comma (or custom) separated file, ending C<.csv> or C<.db>; can be
  377: gzipped (C<.csv.gz> or C<.db.gz>).
  378: B<Note:> the default separator is C<!> not C<,> for historical
  379: reasons - pass C<< sep_char => ',' >> for standard CSVs.
  380: Requires L<Text::xSV::Slurp> for the slurp fast-path (loaded lazily).
  381: 
  382: =item 6. C<Excel> (C<.xls>) and C<XLSX> (C<.xlsx>)
  383: 
  384: Two separate Excel backends - one per file format:
  385: 
  386: =over 4
  387: 
  388: =item B<.xls> - old binary format, opened via L<DBD::Excel> (which uses
  389: L<Spreadsheet::ParseExcel> internally).  All queries go through DBI/SQL;
  390: no in-memory slurp path.  C<max_slurp_size> has no effect.
  391: 
  392: =item B<.xlsx> - modern OOXML format, parsed directly via
  393: L<Spreadsheet::ParseXLSX> and slurped into an in-memory hash (keyed mode)
  394: or array (C<no_entry> mode).  No DBI handle is created; all queries use
  395: the in-memory fast-path.  Complex criteria (operator hashes, C<-or>/C<-and>)
  396: will fall through to the SQL path and croak - use simple scalar criteria.
  397: 
  398: =back
  399: 
  400: For both formats, each worksheet is a separate logical table; the active
  401: worksheet is determined by the class-derived table name (or the C<table>
  402: constructor parameter).  Both modules are loaded lazily.
  403: 
  404: =item 7. C<XML>
  405: 
  406: File ending C<.xml>.
  407: Requires L<XML::Simple> for the slurp fast-path (loaded lazily).
  408: 
  409: =item 8. C<JSON>
  410: 
  411: File ending C<.json>, slurped into memory via L<JSON::MaybeXS> (loaded
  412: lazily).
  413: 
  414: The file may contain either a JSON array of row objects:
  415: 
  416:     [
  417:       { "entry": "key1", "col": "val1" },
  418:       { "entry": "key2", "col": "val2" }
  419:     ]
  420: 
  421: or a JSON object whose keys are the primary-key values:
  422: 
  423:     {
  424:       "key1": { "col": "val1" },
  425:       "key2": { "col": "val2" }
  426:     }
  427: 
  428: In the object form, each key is injected into its row hash under the C<id>
  429: column name (default C<entry>), so all normal lookups work identically to
  430: the array form.
  431: 
  432: A zero-byte or whitespace-only file is treated as empty - all query methods
  433: return 0 / C<undef> / C<[]> without throwing.
  434: Requires L<JSON::MaybeXS> (loaded lazily).
  435: 
  436: =item 9. C<BerkeleyDB>
  437: 
  438: Binary key-value file ending C<.db>.
  439: 
  440: =item 10. C<HTML>
  441: 
  442: HTML page fetched via a C<url>.  Pass C<url => 'https://...'> instead of
  443: C<directory>; the module fetches the page with L<LWP::UserAgent::Cached>, parses all
  444: C<< <table> >> elements with L<HTML::TableExtract>, and slurps the first (or
  445: C<html_table_index>-selected) table into memory.  The first row of the table
  446: is treated as column headers.  Both modules are loaded lazily and are not
  447: required for other backends.
  448: 
  449: =back
  450: 
  451: Pass C<dsn> to bypass file detection entirely and connect via any DBI driver.
  452: Pass C<url> to fetch and slurp data from a remote source without a local
  453: directory.  When the URL returns C<Content-Type: application/json> or the URL
  454: path ends in C<.json>, the response is parsed as JSON (see item 8 above).
  455: Otherwise the response is parsed as an HTML page (item 10).

  468: =head1 QUERY CRITERIA
  469: 
  470: All select methods (C<selectall_arrayref>, C<selectall_array>,
  471: C<fetchrow_hashref>, C<count>) accept the same criteria syntax.
  472: 
  473: =head2 Plain value
  474: 
  475:     status => 'active'          # status = 'active'
  476:     name   => undef             # name IS NULL
  477: 
  478: Values containing C<%> or C<_> are matched with C<LIKE>:
  479: 
  480:     name => 'A%'                # name LIKE 'A%'
  481: 
  482: =head2 Comparison operator hashref
  483: 
  484:     score => { '>'  => 90  }   # score > 90
  485:     score => { '<'  => 50  }   # score < 50
  486:     score => { '>=' => 80  }   # score >= 80
  487:     score => { '<=' => 100 }   # score <= 100
  488:     score => { '!=' => 0   }   # score != 0
  489: 
  490: Multiple operators on one column are ANDed:
  491: 
  492:     score => { '>' => 60, '<' => 90 }   # 60 < score < 90
  493: 
  494: =head2 Pattern matching
  495: 
  496:     name => { -like     => 'A%'  }   # name LIKE 'A%'
  497:     name => { -not_like => 'Z%'  }   # name NOT LIKE 'Z%'
  498: 
  499: =head2 Set membership
  500: 
  501:     name => { -in     => ['Alice', 'Bob'] }   # name IN (...)
  502:     name => { -not_in => ['Alice', 'Bob'] }   # name NOT IN (...)
  503:
