  113: =head1 DESCRIPTION
  114: 
  115: C<Database::Abstraction> is a read-only ORM for Perl that gives a uniform
  116: interface over CSV, PSV, TSV, JSON, XML, SQLite, DBM::Deep, BerkeleyDB, and
  117: Excel (XLS/XLSX) files - local, remote (via SSH), or fetched from a URL -
  118: without writing any SQL.
  119: Effectively it allows you to access a database table, of many different
  120: database formats, as an object.
  121: 
  122: Key features:
  123: 
  124: =over 4
  125: 
  126: =item *
  127: 
  128: B<No SQL required.>  Use plain Perl method calls for simple lookups and
  129: scans; switch storage formats without changing application code.
  130: 
  131: =item *
  132: 
  133: B<Rich query criteria.>  Pass plain values, SQL wildcards, C<undef> (IS NULL),
  134: comparison operators (C<< > >> C<< < >> C<< >= >> C<< <= >> C<!=>), pattern
  135: operators (C<-like>, C<-not_like>), set operators (C<-in>, C<-not_in>,
  136: C<-between>), and logical groupings (C<-or>, C<-and>).
  137: 
  138: =item *
  139: 
  140: B<Automatic joins.>  Add a C<join> parameter to any select method to
  141: combine tables with INNER, LEFT, RIGHT, FULL, or CROSS joins.
  142: 
  143: =item *
  144: 
  145: B<Chained query builder.>  The C<query()> method returns a
  146: L<Database::Abstraction::Query> object for fluent, composable queries:
  147: C<< $db->query->where(...)->order_by(...)->limit(...)->all() >>.
  148: 
  149: =item *
  150: 
  151: B<Aggregation.>  The C<aggregate()> method and the fluent
  152: C<< ->group_by()->measure()->having()->all() >> chain push C<GROUP BY> to
  153: SQL backends and fold rows in Perl on slurp-only backends.
  154: 
  155: =item *
  156: 
  157: B<Schema introspection.>  C<columns()> lists column names; C<schema()>
  158: returns full type/nullability metadata, using native driver introspection
  159: (C<PRAGMA table_info> for SQLite, C<column_info> for others).
  160: 
  161: =item *
  162: 
  163: B<DSN portability.>  Pass a C<dsn> (plus optional C<username>/C<password>)
  164: to connect to any DBI-supported database (SQLite, PostgreSQL, MySQL, ...)
  165: instead of pointing at a local file.
  166: 
  167: =item *
  168: 
  169: B<Performance.>  Small files are slurped into a RAM hash for sub-millisecond
  170: lookups.  All DBI statement handles are cached with C<prepare_cached()>.
  171: A CHI-compatible cache layer is also supported.
  172: 
  173: =back

  305: =head1 FILE FORMATS
  306: 
  307: The module probes the C<directory> for files in this priority order:
  308: 
  309: =over 4
  310: 
  311: =item 1. C<SQLite>
  312: 
  313: File ending C<.sql>, C<.sqlite>, or C<.sqlite3>.
  314: Requires L<DBD::SQLite>.
  315: 
  316: =item 2. C<Deep>
  317: 
  318: DBM::Deep file ending C<.dbm> or C<.deep>.  The entire file is slurped
  319: into a plain Perl hash on open; all in-memory fast-paths apply.
  320: Requires L<DBM::Deep> (loaded lazily).
  321: 
  322: =item 3. C<PSV>
  323: 
  324: Pipe-separated file, ending C<.psv>.
  325: 
  326: =item 4. C<TSV>
  327: 
  328: Tab-separated file, ending C<.tsv>.
  329: 
  330: =item 5. C<CSV>
  331: 
  332: Comma (or custom) separated file, ending C<.csv> or C<.db>; can be
  333: gzipped (C<.csv.gz> or C<.db.gz>).
  334: B<Note:> the default separator is C<!> not C<,> for historical
  335: reasons - pass C<< sep_char => ',' >> for standard CSVs.
  336: Requires L<Text::xSV::Slurp> for the slurp fast-path (loaded lazily).
  337: 
  338: =item 6. C<Excel> (C<.xls>) and C<XLSX> (C<.xlsx>)
  339: 
  340: Two separate Excel backends - one per file format:
  341: 
  342: =over 4
  343: 
  344: =item B<.xls> - old binary format, opened via L<DBD::Excel> (which uses
  345: L<Spreadsheet::ParseExcel> internally).  All queries go through DBI/SQL;
  346: no in-memory slurp path.  C<max_slurp_size> has no effect.
  347: 
  348: =item B<.xlsx> - modern OOXML format, parsed directly via
  349: L<Spreadsheet::ParseXLSX> and slurped into an in-memory hash (keyed mode)
  350: or array (C<no_entry> mode).  No DBI handle is created; all queries use
  351: the in-memory fast-path.  Complex criteria (operator hashes, C<-or>/C<-and>)
  352: will fall through to the SQL path and croak - use simple scalar criteria.
  353: 
  354: =back
  355: 
  356: For both formats, each worksheet is a separate logical table; the active
  357: worksheet is determined by the class-derived table name (or the C<table>
  358: constructor parameter).  Both modules are loaded lazily.
  359: 
  360: =item 7. C<XML>
  361: 
  362: File ending C<.xml>.
  363: Requires L<XML::Simple> for the slurp fast-path (loaded lazily).
  364: 
  365: =item 8. C<JSON>
  366: 
  367: File ending C<.json>, slurped into memory via L<JSON::MaybeXS> (loaded
  368: lazily).
  369: 
  370: The file may contain either a JSON array of row objects:
  371: 
  372:     [
  373:       { "entry": "key1", "col": "val1" },
  374:       { "entry": "key2", "col": "val2" }
  375:     ]
  376: 
  377: or a JSON object whose keys are the primary-key values:
  378: 
  379:     {
  380:       "key1": { "col": "val1" },
  381:       "key2": { "col": "val2" }
  382:     }
  383: 
  384: In the object form, each key is injected into its row hash under the C<id>
  385: column name (default C<entry>), so all normal lookups work identically to
  386: the array form.
  387: 
  388: A zero-byte or whitespace-only file is treated as empty - all query methods
  389: return 0 / C<undef> / C<[]> without throwing.
  390: Requires L<JSON::MaybeXS> (loaded lazily).
  391: 
  392: =item 9. C<BerkeleyDB>
  393: 
  394: Binary key-value file ending C<.db>.
  395: 
  396: =item 10. C<HTML>
  397: 
  398: HTML page fetched via a C<url>.  Pass C<url => 'https://...'> instead of
  399: C<directory>; the module fetches the page with L<LWP::UserAgent::Cached>, parses all
  400: C<< <table> >> elements with L<HTML::TableExtract>, and slurps the first (or
  401: C<html_table_index>-selected) table into memory.  The first row of the table
  402: is treated as column headers.  Both modules are loaded lazily and are not
  403: required for other backends.
  404: 
  405: =back
  406: 
  407: Pass C<dsn> to bypass file detection entirely and connect via any DBI driver.
  408: Pass C<url> to fetch and slurp data from a remote source without a local

  410: path ends in C<.json>, the response is parsed as JSON (see item 8 above).

 4943: =head1 COMMON PITFALLS
 4944: 
 4945: The following mistakes cause unexpected behaviour in common usage.
 4946: Read this section before filing a bug report.
 4947: 
 4948: =over 4
 4949: 
 4950: =item B<Default CSV separator is C<!>, not C<,>>
 4951: 
 4952: For historical reasons the module defaults to bang (C<!>) as the
 4953: field separator for CSV files.  Standard RFC 4180 comma-separated
 4954: files require you to pass C<< sep_char => ',' >> in your subclass
 4955: constructor.
 4956: 
 4957:     sub new {
 4958:         my ($class, %args) = @_;
 4959:         return $class->SUPER::new(sep_char => ',', %args);
 4960:     }
 4961: 
 4962: =item B<Primary key column is named C<entry>, not C<key>>
 4963: 
 4964: The default primary-key column name is C<entry> because C<key> is
 4965: a reserved word in SQL.  If your data uses a different column name
 4966: (e.g. C<id>, C<customer_id>), pass C<< id => 'customer_id' >> to
 4967: C<new()>.
 4968: 
 4969: =item B<Duplicate primary keys silently overwrite earlier rows>
 4970: 
 4971: In slurp mode the entire data file is loaded into a Perl hash keyed
 4972: by the C<entry> column.  If two rows share the same key value the
 4973: second row replaces the first.  To keep duplicates either disable
 4974: slurp with C<< max_slurp_size => 0 >> or switch to a C<no_entry>
 4975: schema.
 4976: 
 4977: =item B<Operator-hash criteria do not work on no-DBI backends>
 4978: 
 4979: No-DBI backends (XLSX, DBM::Deep, JSON, HTML URL, Redis) have no SQL
 4980: engine.  Criteria that use operator hashes (e.g.
 4981: C<< score => { '>=' => 80 } >>) trigger the SQL path and will croak
 4982: with a "meaningless on a NoSQL database" error.  Use simple scalar
 4983: criteria (C<< score => 80 >>) on these backends.
 4984: 
 4985: =item B<Read-only results: do not modify returned hashrefs>
 4986: 
 4987: Unless you pass C<< no_fixate => 1 >>, every hashref returned by
 4988: C<selectall_arrayref>, C<fetchrow_hashref>, and similar methods is
 4989: made read-only by C<Data::Reuse>.  Attempting to assign a value to
 4990: a key in the returned hashref will throw an exception.  If you need
 4991: to modify a row, either copy it first (C<my %row = %{$orig_row}>) or
 4992: construct the object with C<< no_fixate => 1 >>.
 4993: 
 4994: =item B<C<where()> calls in the query builder use AND semantics>
 4995: 
 4996: Each call to C<< $q->where(...) >> adds an additional required
 4997: condition.  Two separate C<where()> calls do NOT produce OR
 4998: semantics.  To express OR, pass C<< -or => [...] >> inside a single
 4999: C<where()> call:
 5000: 
 5001:     # Wrong: this is AND, not OR
 5002:     $q->where(status => 'active')->where(status => 'pending');
 5003: 
 5004:     # Correct: OR grouping inside one where() call
 5005:     $q->where(-or => [{ status => 'active' }, { status => 'pending' }]);
 5006: 
 5007: =item B<C<aggregate()> C<sort_by> must name a grouped or aliased column>
 5008: 
 5009: The C<sort_by> parameter for C<aggregate()> only accepts column names
 5010: from the C<by> list or measure C<as> aliases.  You cannot sort
 5011: aggregate results by a raw data column that is not part of the group.
 5012: This restriction applies equally to the C<< ->order_by() >> call on a
 5013: query builder that has C<measure()> methods set.
 5014: 
 5015: =item B<C<sort_by> is not an argument to the query builder's C<all()>>
 5016: 
 5017: When using the fluent query builder to build an aggregate query, set
 5018: the sort column via C<< ->order_by('col') >> before calling
 5019: C<< ->all() >>.  Passing C<< ->all(sort_by => 'col') >> has no
 5020: effect because the C<all()> terminal method ignores extra arguments.
 5021: 
 5022: =item B<C<Params::Get> positional mapping with C<no_entry = 0>>
 5023: 
 5024: When C<no_entry> is false (the default), the first positional argument
 5025: to C<selectall_arrayref> and C<fetchrow_hashref> is silently mapped to
 5026: the C<entry> key.  Passing an operator-hash criteria in that position
 5027: (e.g. C<selectall_arrayref(status => { '!=' => 'x' })>) causes
 5028: C<status> to be treated as the entry value rather than a column name,
 5029: which will produce wrong results.  Always pass a hashref of criteria
 5030: as a single reference, or use C<no_entry => 1> in your subclass.
 5031: 
 5032: =back

 5035: 
 5036: =over 4
 5037: 
 5038: =item B<Column names> must match the pattern C<[a-zA-Z_][a-zA-Z0-9_.]*>.
 5039: Only ASCII letters, digits, underscores, and dots (for qualified names

 5058: C<Encode::decode('UTF-8', $val)> in your application.

 5069: Unicode scalars.  Emoji in cell values are fully supported.
 5070:

 5072: returns them as-is.  Decode with Encode if the page is UTF-8.
