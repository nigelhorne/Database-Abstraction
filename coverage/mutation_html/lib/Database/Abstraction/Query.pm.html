   72: =head1 DESCRIPTION
   73: 
   74: C<Database::Abstraction::Query> is a fluent query builder returned by
   75: C<< $db->query() >>.  You assemble a query by chaining builder methods,
   76: then execute it with a terminal method.
   77: 
   78: =over 4
   79: 
   80: =item *
   81: 
   82: B<Builder methods> (C<select>, C<where>, C<join>, C<order_by>, C<limit>,
   83: C<offset>, C<group_by>, C<measure>, C<having>) all return C<$self>, so
   84: calls can be chained in any order.
   85: 
   86: =item *
   87: 
   88: B<Terminal methods> (C<all>, C<first>, C<count>) assemble the SQL, execute
   89: it, and return the result.  Each terminal method can be called on the same
   90: builder object independently - calling C<first()> does not modify the stored
   91: state (it temporarily sets LIMIT 1 internally).
   92: 
   93: =item *
   94: 
   95: C<where()> calls are B<merged with AND semantics>: each call adds more
   96: required conditions.  To express OR conditions pass C<< -or => [...] >> as a
   97: key inside a single C<where()> call.
   98: 
   99: =item *
  100: 
  101: The C<join> parameter accepts the same spec as the C<join> parameter in
  102: L<Database::Abstraction/QUERY CRITERIA>.
  103: 
  104: =item *
  105: 
  106: BerkeleyDB backends support C<all()>, C<first()>, and C<count()> with
  107: C<where()> criteria and C<order_by()>/C<limit()>/C<offset()> applied in Perl.
  108: The C<join()> builder method and the C<select()> column projection are not
  109: supported on BerkeleyDB and will raise an error.
  110: 
  111: =back

  789: =head1 COMMON PITFALLS
  790: 
  791: =over 4
  792: 
  793: =item B<C<where()> is AND, not OR>
  794: 
  795: Each call to C<where()> ANDs with all previous C<where()> calls.
  796: Use C<< -or => [...] >> inside a single C<where()> call for OR logic.
  797: 
  798: =item B<C<measure()> calls accumulate>
  799: 
  800: Every C<measure()> call appends a new measure to the query.  To
  801: build a fresh aggregate query call C<< $db->query() >> again rather
  802: than re-using the same builder object.
  803: 
  804: =item B<C<group_by()> replaces, not appends>
  805: 
  806: Calling C<group_by()> a second time replaces the previous group-by
  807: columns entirely.  It does not accumulate like C<measure()> or
  808: C<where()>.
  809: 
  810: =item B<C<count()> is unavailable after C<measure()>>
  811: 
  812: Once you have called C<measure()> on a query builder, calling
  813: C<count()> will croak.  Use C<all()> and check C<scalar @{$rows}>.
  814: 
  815: =item B<Sort column for aggregate queries must use C<order_by()>>
  816: 
  817: To sort aggregate results, call C<< ->order_by('col') >> on the
  818: builder before C<< ->all() >>.  Passing C<sort_by> directly to
  819: C<all()> has no effect because the terminal method ignores extra
  820: arguments.
